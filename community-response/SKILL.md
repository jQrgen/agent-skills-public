## Community Response

This skill helps DevRel team members craft responses to community interactions across forums, social media, GitHub/GitLab issues, Discord, Reddit, and other channels. A great community response is fast, human, accurate, and leaves the person feeling heard — even when the answer is "not yet" or "that's a bug."

### Response Structure

When asked to draft a community response, produce:

1. **Channel context** — Where this response will be posted and any platform-specific tone adjustments.
2. **Sentiment read** — Is the person frustrated, curious, excited, or confused? Name it.
3. **Draft response** — The actual reply, ready to post or lightly edit.
4. **Escalation recommendation** — Should this be routed to support, product, engineering, or legal?
5. **Content opportunity** — Is there a blog post, doc update, or FAQ entry this interaction suggests?

### Tone Guidelines by Channel

| Channel | Tone | Key Principle |
|---------|------|---------------|
| GitLab issues / MRs | Professional, precise | Acknowledge, clarify, next step |
| Forum (GitLab Community, Stack Overflow) | Helpful, thorough | Answer the question fully; link to docs |
| Twitter / X | Concise, warm | 280 chars; never argue publicly |
| LinkedIn | Professional, measured | Represent the company; avoid controversy |
| Reddit | Conversational, humble | Redditors distrust marketing; be a human |
| Discord / Slack | Casual, fast | Emoji OK; follow up in thread |
| Hacker News | Factual, no spin | HN readers are technical and skeptical |

### Response Principles

- **Acknowledge first.** Before answering, show you understood the question or frustration.
- **Be honest about limitations.** "We don't support that yet" is better than a vague non-answer.
- **Never argue publicly.** If a conversation turns hostile, move it to DM or a support ticket.
- **Don't over-promise.** Avoid "we're working on it" unless you can confirm it's on the roadmap.
- **Link, don't paste.** Point to docs, issues, or examples rather than reproducing long content inline.
- **Close the loop.** If you say you'll follow up, follow up.

### Handling Criticism

1. **Read charitably.** Assume frustration comes from a real problem, not bad faith.
2. **Validate the experience.** "That sounds frustrating" is not an admission of fault.
3. **Separate the person from the problem.** Respond to the issue, not the tone.
4. **Offer a path forward.** A support ticket, a workaround, or a timeline — give them something.
5. **Know when to stop.** If a thread is going in circles, disengage gracefully.

### Escalation Paths

| Situation | Route to |
|-----------|----------|
| Bug report with reproduction steps | Engineering / issue tracker |
| Billing or account issue | Support |
| Security vulnerability | Security team (private disclosure) |
| Legal / IP / licensing question | Legal |
| Feature request with strong community signal | Product team + link to existing issue |
| Press / analyst inquiry | Communications / PR |

### Content Opportunity Signals

Flag a community interaction as a content opportunity when:
- The same question appears 3+ times in a week
- The answer requires more than 3 paragraphs
- The question reveals a gap in existing documentation
- The interaction generates significant engagement (likes, replies, upvotes)
